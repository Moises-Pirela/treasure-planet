# Treasure Planet

A first-person multiplayer MMORPG in C-style C++. Players gather in a hub world and physically board ships: each planet has its own ship, and you get there by walking onto its deck and riding it through space. Eventually players build their own ships, fly them anywhere, carry each other and run whole economies. [ROADMAP.md](ROADMAP.md) has what is planned.

**This is the foundation.** You can walk around the hub, board any of the three ships, ride to its planet, walk around the landing pad and ride back, alone or on a server with other players, who appear as capsules. The server is authoritative: clients send inputs and receive the world.

## Build and run

The Vulkan headers, the Vulkan function loader (volk) and GLFW are all in the repository, and the compiled shaders are meant to be too, so that no machine needs the Vulkan SDK to build or play; the SDK is for compiling shaders after editing them (the build does it by itself when it finds `glslc`) and for validation layers. Each platform needs a compiler, CMake, and a graphics driver:

**Windows:** Visual Studio with the C++ tools and its CMake component.

```powershell
.\build.ps1            # debug build, then the tests. -Release for optimised
build\debug\treasure_planet.exe                 # alone: Vulkan, falling back to OpenGL
build\debug\treasure_planet.exe --renderer gl
```

**Linux (X11, or Wayland through XWayland):**

```sh
sudo apt install build-essential cmake libx11-dev libxrandr-dev libxinerama-dev libxcursor-dev libxi-dev libvulkan1 mesa-vulkan-drivers
./build.sh             # debug build, then the tests. --release for optimised
build/debug/treasure_planet
```

A VM without GPU passthrough still runs the game, slowly, on Mesa's software drivers. For a machine that only runs the server, the simulation and the tests, `./build.sh --headless` needs just a compiler and CMake. Configure with `-DTP_WAYLAND=ON` for native Wayland, which also needs `libwayland-dev` and `libxkbcommon-dev`.

**macOS:** the Xcode command line tools, plus CMake and MoltenVK, which implements Vulkan on top of Metal. `build_mac.sh` says what is missing, and `--deps` installs it with Homebrew; it takes the same flags as `build.sh`.

```sh
./build_mac.sh --deps  # debug build, then the tests. --release for optimised
build/debug/treasure_planet
```

macOS only runs the Vulkan backend, because its OpenGL stops at 4.1 and this game's needs 4.5.

Multiplayer is a server and any number of clients (paths as on Windows; Linux and macOS drop the `.exe`):

```powershell
build\debug\treasure_server.exe                           # listens on UDP 27500
build\debug\treasure_planet.exe --connect 127.0.0.1        # one window per player
build\debug\treasure_planet.exe --connect 127.0.0.1        # ...so start two
build\debug\treasure_bots.exe --connect 127.0.0.1 --count 50    # headless players, for load
```

`treasure_server` takes `--port N`, `--max-clients N` (default 64), `--interest METRES` (only tell a client about players and loot within that distance of it, and `--forget SECONDS` before something that went beyond it is dropped; the default sends everyone), `--bandwidth KB/S` (per client, default 32), `--total-bandwidth KB/S` (for the whole server, shared out), `--per-ip N` (handshakes a second from one address, default 10; 0 for none, which a load test from one machine needs), `--trace` (log every player's position once a second) and, for several servers sharing the universe, either `--zones FILE --zone NAME` or `--directory HOST:PORT --zone NAME --owns PLACE,...` (see Multiplayer below). With a directory running, clients need no server address: `treasure_planet --directory HOST:PORT` asks it for the hub. `--name NAME` is what other players see you as. The window title shows the connection state, the player count, the input round trip, the zone hand-offs so far and the tag count; a click is a swing that tags whoever is within three metres in front of you.

| Input | Action |
| --- | --- |
| Mouse | Look |
| W A S D | Walk |
| Space | Jump |
| Click | Swing (tag the player in front of you) |
| F1 / I | Start a party / invite the player you are looking at |
| F2 / F4 | Accept / decline an invitation |
| F3 | Leave the party |
| Esc / click | Release / recapture the mouse |

Ships keep a timetable, so be aboard before they leave. The window title shows the nearest ship and its countdown. To board, walk down a pier from the north edge of the hub (straight ahead from where you start) and through the gap in the ship's stern.

Each planet has a dungeon behind a door on its landing pad. Walking through it puts you in an instance of your own, a string of rooms generated from the dungeon's name, and the glowing slab at the far end brings you back to the pad.

## Layout

```
src/ecs/        the ECS, ported from clockwork-c
src/game/       the simulation: components, systems and the universe's content. No window, no renderer
src/net/        the multiplayer stack: UDP transport, wire protocol, snapshots, zones and tickets,
                the zone server, the predicting client
src/server/     the headless server executable
src/directory/  the zone directory executable
src/tools/      the bots executable
src/render/     the renderer: its data-oriented facade, the frame preparation, the shaders, and the two backends
src/platform/   window, input and graphics setup, on GLFW
src/client/     the game loop: input in, ticks or packets, draws out
tests/          headless tests of the ECS, the game, the renderer's frame preparation, and the whole network stack over loopback
tools/          shader compilation, capture comparison
third_party/    GL and Vulkan headers, volk, GLFW
```

The dependencies point one way: `client -> net -> game -> ecs`, and `client -> render -> platform`. The game and the network stack cannot see the renderer or the window, so the server links `tp_net` alone and runs anywhere.

## Style

C-style C++20: plain structs and free functions. No classes with behaviour, templates, exceptions, RTTI or standard library containers, and the build enforces the exceptions and RTTI parts (`/GR- /EHs-c-`, plus `/W4 /WX`). C++ is used for the small conveniences it offers over C, like struct names without `typedef`.

## The ECS

`src/ecs` is the core of [clockwork-c](https://github.com/Moises-Pirela/clockwork-c) (commit `4602476`) ported to C++, keeping its `cw_` API and behaviour: sparse component pools with stable addresses, cached queries, change observers, command buffers, snapshots, ordered systems with host/client authority, and a fixed-step clock. Its header documents the API and guarantees in detail. Reflection, scenes, assets and game modules were left behind, because they exist to serve clockwork's editor.

## The simulation

All game state lives in one `cw_world`, and everything shares one coordinate space. **Nothing teleports and no level is loaded:** a planet is a place, and a ship is a thing that really flies there.

A ship is a timetable plus a volume. It waits at a dock, then flies a rise, cruise and descend path to the other end of its route. Whatever is inside its volume when it moves gets moved with it. That one rule is the whole of boarding: walk onto the deck and you travel, with no prompt or state change, and any number of players can ride together. Decks are flush with piers and pads, so getting on and off is plain walking.

Adding a planet with its ship is one row in `PLANETS` in [universe.cpp](src/game/universe.cpp).

## Multiplayer

The server is the only authority. A client sends inputs and receives the world; what it simulates itself, it simulates only to hide latency, and the server's word replaces it whenever they disagree. The same `game` code runs in both roles: a `CW_HOST` game owns the truth, a `CW_CLIENT` game is a replica that predicts what it can.

**Transport.** Everything goes over one UDP socket per peer, in packets of at most 1200 bytes ([net.h](src/net/net.h)). A connection carries four **channels**, chosen per message: *unreliable* (keepalives, the handshake), *sequenced* (unreliable, but an older message arriving after a newer one is dropped: snapshots, inputs), *reliable* (delivered exactly once, as soon as it arrives, retransmitted until acknowledged: a character's gear, which carries its own version and must not wait behind a baseline) and *reliable ordered* (held back until everything before it has come: the welcome, spawns and despawns, updates, commands). Every channel numbers its messages in its own space; the two reliable channels are acknowledged with a latest-sequence-plus-bitfield in every packet, so a lost ack costs nothing and a message received out of order is never resent, and an ack owed goes out at once rather than waiting for the next packet that happens to leave. A 64-message window is in flight per channel with a backlog behind it. A message larger than a packet is **fragmented** into pieces that travel as messages of their own on the same channel and are put together again on the other side (up to about 70 KB; a partial message is let go of after three seconds or when a newer one needs its slot). The wire format is explicit, little-endian, field by field ([protocol.h](src/net/protocol.h)); no struct is ever copied raw, so a Windows client and a Linux server agree.

**Round trip and loss.** Every packet carries its own sequence and an ack of the peer's (the latest received, a bitfield of the 32 before it, and how long ago the latest came). The first ack naming a packet gives a round trip sample, less the time the peer held it; smoothed with its variance the way TCP does it, that sets the retransmission timeout (50 ms to a second). A packet the bitfield has passed by without naming is lost; a moving average of that is the loss rate. Both are per connection and visible (`rtt`, `loss`, `packets_lost`), in the client's title bar and the bots' reports, beside the input round trip the game measures for itself.

**Congestion control, pacing, scheduling.** A connection sends at a rate between a floor (an eighth of its cap) and its cap: cut by a quarter, at most once per round trip, when the loss rate passes 3% or the round trip climbs 50 ms above the least seen lately, and raised by a tenth of the cap after every calm second. Snapshots are sized to that rate, so under congestion a client gets fewer players per snapshot rather than late ones. What leaves is **paced**: besides the budget bucket (a quarter second's worth may go at once, for a burst of snapshots and spawns) there is a pacing bucket with a burst of two packets, so a baseline of forty packets leaves two at a time at the rate rather than eight packets in one go. Within the budget, a **priority scheduler** builds each packet: what is in the packet under construction already (snapshots, inputs), then reliable messages high before normal before low; the ordered channel goes in sequence and is as urgent as its next message. The baseline is sent low, so a despawn or a gear change that comes up meanwhile overtakes it. Reliable traffic has first claim on the budget and never exceeds it; acks and keepalives always go.

**Packet validation.** A packet is heard only if it passes, in this order: the header (magic, version, session), the inbound rate limit, the authentication tag, the replay window, and exact framing (every message header and payload inside the packet, nothing left over). A packet failing any of these is dropped whole, with a counter for each reason (`packets_rejected`, `_throttled`, `_forged`, `_replayed`, `_malformed`); nothing in it is delivered and no ack in it is believed. [tests/test_net.cpp](tests/test_net.cpp) feeds a connection every truncation of a valid packet, two thousand one-byte mutations of it and five hundred packets of garbage, in the clear and encrypted, and checks that nothing crashes, that nothing forged gets through the tag, and that every packet is accounted for by exactly one counter.

**Rate limiting.** Outbound, each connection has a **bandwidth cap** (a token bucket; the server's default is 32 KB/s per client, and `--total-bandwidth` shares a server-wide budget out among its clients on top): unreliable messages that would exceed it are dropped rather than sent late, reliable ones are paced and have first claim on the budget (a stream of records is never starved by snapshots), and snapshots are sized to their share of it, farthest players first. Inbound, each connection has a cap on what its peer may send (200 packets and 32 KB a second, with a second's burst; a client sends sixty packets and 2 KB), checked before any decryption, so that a flood from a connected peer costs a comparison per packet. Traffic with no connection yet (handshakes, directory queries) is limited **per address** ([net_limiter](src/net/net.h): a fixed table of token buckets keyed by the ip; ten a second with a burst of thirty at a server, twenty with a burst of a hundred at the directory), and joins are paced at 128 a second whatever arrives. Inputs are quantised (about 2 KB/s upstream).

**Denial of service.** The handshake is built so that an unauthenticated packet is never expensive and never amplifying. A `CONNECT` is answered with a stateless **challenge**: a SipHash of the sender's address and the connect's contents under a key of the server's, rotated every ten seconds, that only whoever receives at that address can repeat; the server keeps nothing and computes one hash. Only a `CONNECT` carrying the right challenge reaches the accept path (the key exchange, the slot, the baseline). So a flood from spoofed addresses gets challenges that go nowhere, a flood from a real address is cut by the per-address limit, and neither fills a slot or costs a multiplication. A `CONNECT` is padded to 600 bytes and every answer to it is smaller, so a server cannot be used to amplify traffic towards a victim. Connected peers are bounded by their inbound caps; reliable queues refuse past a backlog; the client table is a hash, not a scan. What is not covered: volumetric floods beyond the socket (the operating system's problem) and an attacker who can both spoof and receive (on the path), who is the encryption's problem below.

**Connection tokens.** Behind a directory, a zone admits nobody on their own say-so. A client's query for a place carries its platform identity and proof; the directory verifies them ([accounts.h](src/net/accounts.h)) and answers with a **connect token** ([zones.h](src/net/zones.h)): the verified identity, the zone chosen, an expiry a minute away and a nonce, signed with the zone secret. The client presents it with `CONNECT`, opaquely; the zone checks the signature, the zone name and the expiry, remembers the nonce (a token is good once, or again from the same address, which is what a reconnection is), and takes the identity from it, so a shard never verifies a platform's proof itself and nobody joins a shard the directory did not send them to. A hand-off's *ticket* is the same idea issued by a zone: it carries the identity too, and a zone takes either. A client that lost its connection asks the directory for a fresh token for the zone it was on (its own may be stale, or for the zone before a hand-off) and reattaches to its lingering body with it. A standalone server (no directory) verifies platform proofs itself and needs no token.

**Encryption and integrity.** The handshake is an X25519 exchange of ephemeral keys (`CONNECT` carries the client's, `KEYS` the server's and the session id); every packet after it is ChaCha20-Poly1305 under keys derived from the shared secret, with a counter as nonce, the header as associated data, and a window that refuses replays. Both primitives are implemented here ([crypto.h](src/net/crypto.h)) and checked against the RFC 7748 and RFC 8439 test vectors. What travels in the clear is signed instead: tickets, tokens, registrations, tables and introductions carry a SipHash under the zone secret (the signed body says what kind of thing it is, so a token is never read as a ticket), and the challenge is a SipHash under a key the server alone holds. What this gives: nobody on the path reads or alters traffic, forges packets, or replays them; nobody forges a credential. What it does not: the key exchange is unauthenticated, so an active attacker in the path could impersonate a server; fixing that means the directory's public key in the client and its answers encrypted to it, which is the next step.

**Joining.** The client repeats `CONNECT` until the server answers with `KEYS` and then a reliable, encrypted `WELCOME` (the client's player entity, the universe clock, the places), then streams the world as `SPAWN` records and ends with `BASELINE_END`. Entity ids are the server's, mirrored exactly. Joins and leaves arrive later as reliable `SPAWN`/`DESPAWN`.

**Fixed ticks, headless, deterministic.** The simulation is `game_tick` at 60 Hz and nothing else: no renderer, no window, no wall clock inside it (ships read universe time, which is a tick's input like any other). The server is that loop and a socket; the client is that loop, a socket and a renderer looking on. Given the same inputs the same world comes out, whatever the batching: [tests/test_game.cpp](tests/test_game.cpp) runs two worlds through the same scripted inputs, one tick at a time and in batches, and checks that they hash the same at every step. That is what makes prediction a replay rather than a guess, and what would make a recorded match replayable.

**Ownership.** Every player entity carries `Owned {account}`, replicated like any component, so every peer can tell whose body is whose. The server drives an entity only from the connection that owns it: an input message moves the sender's player and nothing else, `EQUIP` changes the sender's gear, and the client side predicts only the entity the `WELCOME` named. There is no message by which a client could name another entity, so there is nothing to validate; ownership is the shape of the protocol.

**Connections.** Both sides send a keepalive after half a second of silence and give up on the other after five. Leaving is a `DISCONNECT` with a reason: a *quit* (the client closed, or its session is being torn down) or a *hand-off* (it is already somewhere else). A quit leaves the body in the world for ten seconds and a lost connection for a minute (`linger_quit`, `linger_timeout`): the body stands where it was, idle, still visible and still tagged by passing swings, with its gear on, and the party and the world it was in remembered. A client that connects again as the same account in that time (the session does this by itself when a server falls silent: up to five attempts, each given ten seconds, the new world built alongside the old and swapped in once it shows where we stand, exactly as a hand-off is) gets that body back, where it left it, with no new spawn, the same gear, and no place in the party lost (the world itself is streamed again, since the client's copy went with its connection); one that arrives by ticket instead replaces it. When the time runs out the body is despawned and the character saved for the last time. The server keeps the counts (`reattached`, `lingered`, `finalized`); [tests/test_net.cpp](tests/test_net.cpp) cuts a client's socket and checks that its body lingers, that the reconnection reattaches to the same entity with the same gear, and that a quit lingers briefly and is then gone.

**Planets have land** ([planet.cpp](src/game/planet.cpp)). A planet's surface is a height field on its sphere: continents where noise of its own frequency passes its sea level, ridged mountains on them, and a flat about the top that its landing pad is set into. It is the simulation's, not the renderer's: players stand on it (`game_ground_y` under the box collisions), what is built on it is placed on it (`game_planet_point`), and the client makes the planet's mesh from that very field, so what is walked on is what is seen. Each planet carries its land in its `Planet` component (replicated like everything else), so a client, a server and a second server all make the same world. Each has one hub for now: the landing pad with its dungeon door, and a monument on the land beyond it, along the line the ship comes in on, so it stands ahead of the deck the whole way down. A *landmark* place names it; the client lights it and the server ignores it.

**Universe time and ships.** Ships follow a timetable read off *universe time*, the wall clock shared by every server and client, rather than integrating their motion. So a ship is a pure function of time: two servers that have never spoken put it in the same place, a client predicts it exactly, and snapshots never mention ships at all. The server's tick is driven by that clock rather than by its own loop: after a stall it catches up (to a second's worth, then skips the rest: ships land where they should, players simply did not move), and after a real clock jump universe time moves with it, so no zone ever drifts from another. `treasure_server --universe-epoch` shifts the clock, for tests; every zone must be given the same value.

**Prediction.** The client runs the real movement systems on its own player, one tick ahead of the server, numbering every input and remembering the position each one led to. The server queues inputs and consumes exactly one per tick (holding two as a jitter buffer), and each snapshot says which input it had applied and how many are still waiting. The client then sets its player to the server's state at that tick, replays the inputs the server has not seen yet with `game_replay_tick`, and compares. Usually the result is identical to the millimetre; when it is not (a collision the server saw first, a late input the server had to repeat), the simulation is corrected at once and the picture catches up through a view offset that fades in a tenth of a second. The replay also anchors the client's tick counter to the server's, which is what keeps the predicted ships where the server has them, passengers included, and the queue depth steers the client's tick rate (by up to a tenth) so that its clock follows the server's rather than its own. Players a client does not own are not simulated: they arrive in snapshots and are rendered 100 ms behind the server's clock (estimated from the fastest snapshots of the last two seconds), interpolated between samples, in the frame of the ship they stand on.

**Lag compensation.** A swing (a click) is the first action where it matters: what you aimed at is where the other player *appeared*, which is where they were a tenth of a second and a trip ago. The server keeps a second of every player's positions, tick by tick, relative to the ship they stood on, and each input says which server tick the client was rendering the others at; a swing is judged against the others where they were at that tick. A shot aimed at where they are drawn lands; one aimed at where the server has them right now (which only a cheat could know) misses. Hits arrive in snapshots, and the tagged player flashes.

**Snapshots** ([snapshot.h](src/net/snapshot.h)) are quantised (millimetres, 16-bit angles) and delta-coded against the last snapshot the client acknowledged: a player standing still costs two bytes, a moving one six or so, and a snapshot that gets lost costs nothing but the next one being coded against an older base. Players are prioritised by distance within the packet budget. Four players walking together is about 1 KB/s each.

**Relevance** is a policy per class of entity, not a special case ([server.h](src/net/server.h), `server_relevance`). Scenery (planets, ships, the places) is always relevant: it is the same everywhere and costs nothing after the baseline. Players and loot are relevant within a radius of the client's player (`--interest`; 0, the default, means everywhere): a player's record is sent the first time it is within reach, and from then on it is in the client's snapshots; loot's record is sent when the client comes near. What has been beyond the radius, plus a quarter of it for hysteresis, for `forget` seconds (`--forget`, default five) is dropped from the client with a `DESPAWN`, and sent afresh, gear and all, if it comes back. The server forgets nothing; only the client's picture of the world is bounded, so its memory and its traffic follow how crowded its surroundings are, not the population of the zone. The pass that judges this is the one pass over the world that chooses the snapshot's contents, so it costs no more than before.

**Records are delta-coded too.** A change to part of an entity, such as the gear a player wears, goes out as an `UPDATE` carrying only the components that changed (a component mask per change, `server_change`), to the clients that have the entity, rather than the whole record again; a client that has dropped the entity in the meantime skips it. Snapshots carry what changes every tick (position, velocity, angles, the hit counts); records carry what changes rarely; nothing carries what never changes.

**Zones** ([zones.h](src/net/zones.h), [server.h](src/net/server.h)). The universe is divided by *place*: the hub, each planet's landing pad. A zone server owns some places and every player standing in them; it simulates the whole static universe and every ship regardless, since those cost nothing and agree everywhere. When a player walks into a place another zone owns, their server issues a *ticket* (their state, signed with the shared secret by SipHash), redirects the client, and freezes the player: inputs are ignored, physics carries on, so the ticket stays true. The client freezes its prediction the same way, connects to the new zone with the ticket, builds the new world alongside the old one, and switches only once the new zone has shown it where it stands, bridging the two predictions with the view offset; then it leaves the old zone, which despawns the frozen body. If the new zone refuses or never answers, the client says so and the old zone thaws the player and tries again later; a client that vanishes mid-way is thawed after four seconds and dropped after five. A ticket is good once (a zone remembers the ones it accepted), and a player arriving by ticket replaces any stale connection of the same account. Servers never talk to each other. A ship flight from the hub to a planet is therefore a hand-off between processes, taking a few tens of milliseconds on a LAN, and [zones.example.txt](zones.example.txt) is everything needed to run two of them. Today a zone is one process and one core; the next step up is several zones per process and a directory service in place of the static file.

```powershell
build\debug\treasure_server.exe --zones zones.example.txt --zone hub
build\debug\treasure_server.exe --zones zones.example.txt --zone planets
build\debug\treasure_planet.exe --connect 127.0.0.1:27500
build\debug\treasure_bots.exe --connect 127.0.0.1:27500 --count 3 --ride --party    # a fireteam rides the ships, runs the dungeons together
```

Or with the directory instead of the file, on one or many machines:

```powershell
build\debug\treasure_directory.exe --secret WORD
build\debug\treasure_server.exe --directory 127.0.0.1:27400 --secret WORD --zone hub --owns hub
build\debug\treasure_server.exe --directory 127.0.0.1:27400 --secret WORD --zone planets --owns Verdant,Ember,Azure --port 27501
build\debug\treasure_planet.exe --directory 127.0.0.1:27400
```

Shards are servers owning the same place, with a region and a target:

```powershell
build\release\treasure_server.exe --directory 127.0.0.1:27400 --secret WORD --zone hub-1 --owns hub --region eu --target 800 --max-clients 1000 --per-ip 0
build\release\treasure_server.exe --directory 127.0.0.1:27400 --secret WORD --zone hub-2 --owns hub --region eu --target 800 --max-clients 1000 --port 27502 --per-ip 0
build\release\treasure_bots.exe --directory 127.0.0.1:27400 --region eu --count 250 --light     # x4 for a thousand
```

(Servers behind a directory admit only clients the directory sent, so bots go through it too; `--per-ip 0` lifts the per-address handshake limit that a thousand clients from one machine would otherwise hit.)

Or let the orchestrator run the shards:

```powershell
build\release\treasure_directory.exe --secret WORD --save characters.bin
build\release\treasure_orchestrator.exe --directory 127.0.0.1:27400 --secret WORD --server build\release\treasure_server.exe --places hub --regions eu --target 800 --capacity 1000
```

**A thousand in the hub.** One zone server holds 1000 players in the hub, at about 40% of a core and 16 KB/s per client ([tests with `treasure_bots --light`](src/tools/bots.cpp)). What makes it fit: snapshots are chosen by priority (distance, discounted by how long since the client last heard of someone), so a client gets its nearest seventy or so every snapshot and everyone else in rotation every few seconds; the choice itself, the one pass over every player, is reused for a few snapshots; a player's record goes out the first time they matter to someone rather than in a baseline of a thousand; the snapshot rate backs off from 20 Hz to 10 and 5 when building them eats the budget, and clients widen their interpolation to match; snapshots are staggered across ticks (a thousand built in one tick would leave the socket unread long enough to overflow, which showed up as 30% loss once the transport could measure it); joins are paced (128 a second, one key operation each, the server's key rotating every ten seconds) so a crowd arriving at once cannot stall the tick; a broadphase grid keeps collision per player to a cell; clients are found by a hash, not a scan. A Release build is needed for any of this: the Debug key exchange alone is seven milliseconds.

**Shards.** Past that, the hub is several zones that own the same place, each a full copy ([zones.h](src/net/zones.h)). A player is sent to the shard their **fireteam** is on if it has room, else to one in their **region**, else anywhere; among those, to the fullest still below its **target**, so that shards fill up one after another and none feels empty, and to the emptiest once all are past their targets. The directory makes the choice when a client asks for a place (it knows every shard's region, population and target from their registrations, and every party from the social service, and counts the players it has just sent somewhere before they show up in that shard's report); a zone makes the same choice for hand-offs, from its table and the party state it holds for the player; a player already on a shard of a place stays on it. Servers declare `--region` and `--target`; clients `--region`. When every shard of a place is at its target the directory says so, which is the signal for an orchestrator (or a person) to start another: the policy is here, the spawning of processes is not.

**The directory** ([directory.h](src/net/directory.h)). In place of the static zones file, `treasure_directory` keeps the table: servers register every two seconds (name, places owned or instance hosting, load, the address to publish), signed with the zone secret, and get the live table back; entries that stop registering expire. Clients ask it which server owns a place (`--directory`), so no server address is ever typed. It also does the **NAT traversal** a home-hosted zone needs: a client asking for a zone is *introduced* to it, meaning the directory tells the server the client's address as seen from outside and the server sends a few packets there, which opens its NAT for the client's packets; the client's own first packet opened its own. Redirects ask for the same introduction to their destination. Symmetric NATs, which change ports per destination, are the case this does not cover; those need a relay.

**Identity and crossplay** ([accounts.h](src/net/accounts.h)). A client presents a *platform identity* (`local:alice`, `steam:7656…`) and the name it wants shown; the provider for the scheme verifies it and the account id is derived from the identity, so the same person is the same account on every server, from any platform. The `local` provider is the development mock; the `steam` provider is a stub that checks the format and marks, in place, the three calls a real one makes (ticket validation, persona name, friends). Names are replicated on players, so everyone sees who is who.

**Parties** ([social.h](src/net/social.h)). Fireteams of up to five span zones, instances and servers, so they live in the **social service**: presence (who is online, where), accounts as a database would keep them, and the parties themselves. It runs inside the directory process; a server without a directory runs one in-process, so parties work alone too. Clients never talk to it: their zone server relays requests (encrypted on the way in, signed on the way on) and passes back the party state whenever it changes for someone it hosts. Inviting is by name, and in the client by *looking at someone* and pressing I; invitations wait a minute; the leader kicks and promotes; members who go offline stay in the party. A party shares a dungeon instance, because the party id is the instance key. Presence reports carry the connection that makes them, so a player's move between servers or worlds cannot be undone by the old connection's last words arriving late.

**The overlay** ([hud.h](src/client/hud.h)) is a mock-up drawn with what the renderer has: every pixel of a 5×7 glyph is a tiny unlit quad a quarter of a metre in front of the eye, in the camera's frame. The party panel sits top right, one member per line: who leads, who you are, where each member is, who is offline, and the last thing the service said no to. A real UI pass (a texture, an orthographic projection) replaces this layer without touching anything behind it; [tests/test_hud.cpp](tests/test_hud.cpp) projects the panel from several cameras and checks it lands where it should.

**Dungeons and instances** ([dungeon.cpp](src/game/dungeon.cpp), [server.h](src/net/server.h)). A server hosts many worlds: its zone's universe, and any number of dungeon *instances*, each a world of its own (rooms, corridors and an exit; no ships, no planets) opened when the first ticket for it arrives and closed a minute after the last player leaves. The door on a planet's pad is an entrance place; walking into it is a hand-off like any other, with a ticket that names the dungeon, an *instance key*, and where the exit should lead. Solo play is the simplest key: the player's own account, so everyone gets a private copy; a party will share a key, and a queue will hand out keys, with nothing else changing. With no instance hosts in the zones file, the zone whose door it is opens the instance itself (the redirect says "this same server", so it works with a single standalone server too); with `instances` lines, instances are spread over those hosts by key, and such a host has no universe at all. The exit is an exit place whose ticket returns the player to the pad in front of the door.

## The renderer

The renderer is a facade over plain data ([renderer.h](src/render/renderer.h)). Meshes go in once; then every frame is handed over whole: a camera, an environment (the sun, the sky, the ambient light), the post-processing stack's settings, a flat array of point lights and a flat array of draws. Nothing is retained between frames, nothing calls back, and the caller never sees a graphics API.

What happens to a frame is in one pure, headless module ([frame.cpp](src/render/frame.cpp)), so that both backends get the same answer and [tests/test_render.cpp](tests/test_render.cpp) can check it without a GPU:

- **The sun's shadows** are cascaded shadow maps, up to four, their count and resolution the sun's data (`shadow_cascades`, `shadow_resolution`), since the shadow pass is the one fixed cost that does not care how simple the scene is. Each cascade is an orthographic box around a slice of the view frustum, bounded by a sphere (so its size does not change as the camera turns) and snapped to its own texel grid (so the shadow's edges hold still as the camera walks). The fragment shader picks the cascade by view distance, samples a 3×3 percentage-closer filter with a small offset along the surface normal, and fades the shadows out at the end of the last cascade so their reach has no edge. Shadow maps are drawn with front faces culled, which is what keeps flat surfaces from shadowing themselves. A draw can leave the shadow maps (`R_DRAW_NO_SHADOW`) and skip the lookup (`R_DRAW_UNSHADOWED`); the client gives both to a planet and its clouds once the camera is more than `PLANET_SHADOW_ALTITUDE` above the land, where a world's own shadows are below a pixel and its hundred thousand triangles would otherwise go through every cascade.
- **The painted light** (`r_shading`, part of the environment): in place of plain Lambert, a ramp that wraps into the dark side and blends, by a *flatness*, between Lambert's gradation and a flat band with a soft terminator (and can be stepped, for a drawn look); a *shadow tint* multiplied into whatever the key light does not reach, so shadows go cool against the warm key rather than black, the film's 70/30; and a *rim* of the sky's colour on every silhouette, stronger on what faces up. Ships, the hub, players and planets all get it; zero is plain Lambert.
- **Point lights** are windowed inverse-square lights with a radius. Any number can be submitted; those whose reach is in view are kept, the nearest `R_MAX_POINT_LIGHTS` (32) of them, nearness counting reach, go to the shader, and every draw carries a bit per light whose reach touches it, so a fragment loops over the lights that can reach it and no other. The client derives its lights from the world rather than storing them in it: loot glows in its rarity's colour, a dungeon's exit slab and the lantern over a dungeon door are lit, and every ship carries a lantern.
- **Culling**: every pass (each cascade, the main view) gets the list of draws whose bounding sphere touches it, as ranges of one index array. An overlay draw (`R_DRAW_UNLIT`) is drawn as is and casts nothing.
- **The sky** is procedural: a gradient from the zenith through the horizon to the ground, then its **layers** (`r_sky_layer`, up to eight, drawn in the order given), then the sun's disc with a glow around it; one triangle at the far plane, drawn last where nothing else was. A layer is a field of *stars* (hashed with integer arithmetic from a seed over a cube of cells, so every GPU and every capture draws the same sky; two fields, one fine and one bright, give depth), a *nebula* (fractal noise cut at a cover into glowing cloud, two colours mixed by a second noise, filaments of ridged noise through it, about a direction within an angular size or washed over the whole sky, turning slowly about an axis), or a *celestial body*: a sphere of an angular size at a direction, lit by the sun so it has a phase and a night side that hides the stars behind it, its albedo two tones banded by noise, light of its own with a glow about it if it is a sun, and rings across its axis (banded, lit, shadowed by the body, hidden behind it and hiding it in front). Inside an atmosphere the stars and nebulae fade by how much of them the air hides and a body mostly does, so a moon is faint by day. The client's space sky is two nebulae, two star fields, a ringed giant, a moon and a red dwarf, in that order.
- **Atmospheres**: each planet's air is a shell of data (`r_atmosphere`: height, the sky from inside, the haze and its density, how many stars it hides, the sun's halo); the facade works out how deep the camera is in the one it is deepest in, and by that depth the sky blends to the planet's, the stars thin out and the sun spreads. The haze is *aerial perspective*: what is seen through an atmosphere fades into its haze by the length of the sight line's way through its air (a ray against the shell, per fragment, for the nearest `R_MAX_AIRS` shells), so from orbit a world is veiled by its whole column of air and its land comes clear as the ship comes down through it, the cloud deck whiting the view out on the way. A ship's descent crosses the shell over the last stretch of its flight and drops through the deck to the pad, so arriving at a world is a gradual thing rather than a cut. **Entering** at speed (the camera's velocity against the air's `entry_speed`, times a band over the depth that is nothing at the shell's edge and at the surface and full half way down) streaks the picture towards where the camera is going and streams sparse plasma past the edges, and the camera shakes; on the way down a **cloud deck** (a band of thick haze of its own colour at an altitude) whites the view out and clears again. Each planet's air, deck and entry are in its `PLANET_LOOKS` row, the look of the entry (blur, streaks, glow) in `r_post.entry`; `--moving X Y Z` gives a capture a velocity, for looking at it.
- **Clouds** are a layer of their own: a second sphere per planet at the cloud deck's altitude with an `R_MATERIAL_CLOUDS` material, drifting noise cut into cloud and hole at its alpha (the anti-aliasing softens the cut), two-sided (`R_DRAW_TWO_SIDED`) so it is a ceiling with holes from the ground and a cover from orbit, lit from behind by its translucency. Its shadow on the land is not a shadow map's but the layer's own: the lit pass follows the way from the fragment to the sun out to the layer's sphere and reads the cover there (`cloud_cover_at`, the same function the material draws by), so a cloud's shadow is the cloud's shape, drifts with it, and costs a noise lookup rather than the whole sphere in every cascade, which was most of the shadow pass; it is there from orbit too, where the shadow maps are not. A two-sided thing takes no shadow itself, since one surface in the shadow map would shadow itself wherever the sun grazes it.
- **Planets have levels of detail**: the client makes each planet's landmass mesh at three resolutions and draws the one for the camera's distance in radii (`PLANET_LODS`), the cloud sphere likewise, so a world on the far side of the sky is a few thousand triangles rather than a hundred and fifty thousand.
- **Shaders are files** ([src/render/shaders](src/render/shaders)): `common.glsl` holds the blocks the facade fills and a few helpers, `noise.glsl` the integer-hashed noise, `lit.glsl` the lit pass's framework, and the stage programs are one file each (`mesh.vert`, `sky.frag`, `post_composite.frag`, …). The build embeds every file; OpenGL compiles from the embedded text at runtime, expanding the `#include`s itself ([shaders.cpp](src/render/shaders.cpp)), and glslc compiles the same files to SPIR-V. Adding a file is adding a shader, and editing one is a rebuild (the files are configure dependencies, so the embedded table is never stale against the C++ layouts it must match).
- **Materials** are a shader and its parameters. A *material shader* is a file in `shaders/materials/` that defines one function, `Surface shade(Fragment f)` — what the surface is at a fragment: albedo, emission, tint, the normal to light by, alpha (cut when the file says `MATERIAL_CUTOUT`), translucency, whether the sky's rim light falls on it — and gets everything else from `lit.glsl`: the sun through the cascaded shadows, the light ramp and shadow tint, the point lights that reach the draw, the rim, the haze, and its own shadow-pass program when it cuts holes. Each is addressable by its stem (`renderer_shader(r, "planet")`) and compiled in both backends. An `r_material` is a shader id and `R_MATERIAL_VEC4S` vec4s the shader reads as it likes; [materials.h](src/render/materials.h) lays out the built-in three (`surface`: the draw's colour with the metre checker; `planet`; `clouds`) as typed structs with a function each. A frame carries a table of materials, a draw names one by index, and the lit pass is sorted by shader so a backend changes program seldom.
- **Models** are parts, each a mesh with a material at a place in the model's frame (`r_model_part`); `renderer_model_draws` lays a model out as draws, which is all a model is to a frame. Meshes come from the generators (cube, sphere, capsule) or from Wavefront OBJ (`renderer_mesh_load_obj`, on a parser that is pure and tested).
- **The planet material** makes a world on its sphere, from noise hashed with integers (the same on every GPU). With `relief` it has **land**, and the mesh arrives already shaped by it: the client builds a planet's mesh from the simulation's own height field (the one players stand on), so the shader only has to colour what is there — sea, land, snow above the line, the flat about the top the landing pad sits in — from the elevation the mesh carries. Without relief it is a gas giant: three tones mixed by latitude bands bent by the noise. Either way clouds may be painted over it, the atmosphere glows at the rim and brighter on the day side (by the sphere's normal, not the land's), lava or city light on the night side, and a tint along the terminator, which is the painterly warm-against-cool of the film. Each planet's look is a row in the client (`PLANET_LOOKS` in [main.cpp](src/client/main.cpp)); a planet not listed is painted from its colour.
- **Colour**: lighting is in linear radiance into a floating-point scene target; what happens to it after is the post-processing stack below. An unlit draw's colour is taken as the colour it should come out as and passes through the stack untouched, which is what the overlay wants.

**The post-processing stack** is data too (`r_post`, and the haze in `r_environment`): every field's zero is off or neutral, so an all-zero stack is a plain copy of the scene with the display's gamma, and no number that shapes the picture lives in a shader. The facade turns it into a flat list of *steps*, each one program, up to three input targets, one output target and four parameters, over a fixed table of render targets (the scene and its twin for the full-size steps to ping-pong between, the scene's depth as a readable target, the bloom's two mip chains, the flare, an 8-bit intermediate, the window); nothing that is off costs a step, and a backend runs each step as one triangle.

- **Outline**: lines where the depth breaks (a silhouette) or the surface turns (a crease), from the depth buffer alone. A plane's stored depth (the near plane over the view depth, since depth is reversed and the far plane is at infinity) is linear across the screen, so its second difference is nothing on a surface and the size of the break at an edge, as a fraction of the depth; creases come from normals rebuilt from the depths either side of the pixel, each from the two pixels beyond it so the crease under the pixel is never crossed, compared across it. Width, the two thresholds, the line's colour and a distance the lines fade by are data; an unlit pixel (the overlay) is left alone and lines nothing next to it. It runs first, so the haze fades the lines with everything else: the drawn look.
- **Haze** (`r_haze`): everything fades into a colour by the density along its line of sight, integrated in closed form: the same below a base height and thinning above it by a falloff (so a ground mist leaves the sky clear overhead and fogs the horizon), none before a start distance, the sky as far away as said or infinitely far; towards the sun it glows in the sun's colour by a power. Per world, not per planet: the dungeon's damp, the faint dust between the hub's piers. (A planet's own air is its atmosphere, shaded per fragment in the lit pass, since it is a shell rather than a height.)

- **Tone mapping and grading**: exposure and white balance, then a curve (clamp, ACES, extended Reinhard or Hable's filmic, with a white point), then on display-linear colour: saturation, contrast about middle grey, lift/gamma/gain per channel, a vignette, and the output gamma.
- **Bloom**: Jimenez's 13-tap downsample down a chain of up to six mips (the first mip thresholds with a soft knee, ignores unlit pixels and weights bright quads down so fireflies do not flicker), then a tent-filtered upsample back up, blending each level with the one below by a *scatter*; then added by an intensity.
- **Lens flare**: made from the picture itself, from one of the bloom's mips: what is bright, mirrored through the centre, repeated along the line to the centre as ghosts with their colours fringed, plus a halo ring; thresholded, faded towards the edges, added by an intensity. A sun behind a wall flares nothing, because nothing bright is there.
- **Chromatic aberration**: the colour channels sampled apart radially, growing with the square of the distance from the centre.
- **Anti-aliasing**: FXAA (in the form Simon Rodriguez set out from Lottes's 3.11), from luma the composite leaves in its alpha, with its thresholds, sub-pixel blend and edge-search length as data; `r_aa_mode` leaves room for MSAA or TAA.

`renderer_timings` says where the GPU's time went, pass by pass (timer queries in OpenGL, timestamps in Vulkan; the post steps by program, so the outline and the haze are lines of their own), and `treasure_planet --stats` prints it once a second, with the frame's time, its worst, and the CPU's time ticking the world and building the draws: the first thing to look at when a frame costs more than it should. `--bench SECONDS` holds one view (`--at`, `--look`) with vsync off and prints the same, for what a frame really costs; it runs the GPU flat out for as long as it is asked to.

The look of each kind of world is two tables in the client (`environment_of` and `post_of` in [main.cpp](src/client/main.cpp)): space has one hard sun and no air to soften it, crisp and cold, a dungeon is lit by a low sun and whatever glows in it, warmer and darker at the edges. `treasure_planet --dungeon "Verdant Depths"` walks a dungeon alone, for looking at it.

A backend ([backend.h](src/render/backend.h)) executes the prepared packet without a decision of its own: the shadow passes, the lit pass, the sky, the post steps, a capture. Two of them:

- **Vulkan 1.1**, loaded at runtime through volk, so machines without a driver still start. On macOS it runs on MoltenVK.
- **OpenGL 4.5** core with direct state access, on Windows and Linux.

Both use the same shader sources and the same conventions: y-up clip space, and reversed depth with an infinite far plane on a 32-bit float buffer, so a deck rail and a distant planet share a depth buffer without fighting. That buffer is the depth target the post steps read (a depth texture in OpenGL, taken off the scene's framebuffer while the steps run; the scene's depth image in Vulkan, left in the read-only layout by the scene pass and sampled unfiltered).

OpenGL compiles the shaders at runtime. Vulkan embeds SPIR-V, one blob per program (every `.vert` and `.frag`, and a lit-pass and a shadow-pass blob per material shader). When the build finds `glslc` (the Vulkan SDK, through `VULKAN_SDK` or the path), it compiles them itself into a table in the build tree; otherwise it uses the table committed in [src/render/shaders/spirv](src/render/shaders/spirv), which carries the hash of the sources it was built from, and the Vulkan backend declines to start (falling back to OpenGL, and saying why) when that is not the hash of the current sources, rather than run stale shaders against the wrong layouts. To refresh the committed table after editing a shader, run `tools\compile_shaders.ps1` or `tools/compile_shaders.sh`, which build it and copy it in.

To check that the backends agree, capture the same scripted scene with each and compare:

```powershell
build\debug\treasure_planet.exe --renderer vulkan --capture vk.bmp --ticks 60
build\debug\treasure_planet.exe --renderer gl --capture gl.bmp --ticks 60
python tools\compare_captures.py vk.bmp gl.bmp 8
```

`--at X Y Z` and `--look YAW PITCH` place the camera. Expect a handful of differing pixels out of 921,600, along triangle edges, because the two APIs break rasterisation ties differently. The last argument is how many differing pixels to allow.
